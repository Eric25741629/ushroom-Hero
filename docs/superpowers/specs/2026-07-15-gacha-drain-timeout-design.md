# 純 WS 一鍵抽完 timeout 修復設計

## 問題與根因

Dashboard 的純 WS 抽卡會送 `0x0902`，並等待 `0x0902` 成功回包或
`0x0201`（十進位 `513`）拒絕回包。`WSTimeoutError` 只代表指定時間內兩種
回包都沒到，不等於 WebSocket 已斷線。

5554 的 CDP live probe 已排除券不足：`0x0401` 顯示技能券 `1012 = 375651`、
同伴券 `1013 = 374148`，第一批 999 消耗 800 後仍足以繼續。真正原因是 dashboard
收到第一個 `0x0902` 後立即送下一個 999；伺服器會把過早到達的第二包靜默丟棄，
既不扣券、不增加抽池 count，也不回 `0x0902`／`0x0201`，最後成為 timeout。

5554 同帳號、相同技能 999 封包的 send-to-send 實測：

- `504.8ms`：第二包靜默丟棄；
- `614.0ms`：第二包靜默丟棄；
- `707.0ms`：第二包靜默丟棄；
- `804.1ms`：第二包成功，兩包合計扣 1600 張券。

因此伺服器可接受門檻位於約 0.71～0.80 秒之間。實作採 1 秒，保留執行緒排程與
網路抖動餘裕；這是 live server 行為，不是照抄前端 500ms 防連點設定。

## 目標

- 一鍵抽完以權威背包餘額選擇 999／35／15，不靠錯誤回包探測券數。
- 所有付費抽卡 request 的送出起點至少相隔 1 秒。
- 區分「伺服器無回應」與「確定斷線」，不再把所有 timeout 稱為斷線或傳輸錯誤。
- timeout 後以券數與抽池 count 探測請求是否落地，不盲目重送。
- fixed 模式維持保守：回包不明時停止，避免重送造成超出指定批數。

## 資料流

1. 工作取得持久 `WSGameClient` 後，以既有 `0x0401` 全背包查詢讀取對應抽券數量。
2. 同時以 `0x0901` 讀取目標 pool 的 `count`，作為 timeout 後的第二確認值。
3. 若背包讀取成功，使用既有固定成本 `999→800`、`35→30`、`15→15` 選擇最大可負擔檔位。
4. 每次送出前，以 monotonic clock 保證本次與前一次 request 起點至少相隔 1 秒。
5. 收到 `0x0902` 成功回包後，從本地權威起始餘額扣除該檔成本，並累加預期 pool count。
6. 餘額低於 15 時以 `exhausted` 正常完成，不再送必定不可負擔的封包。
7. 若起始探測失敗，工作停止並顯示讀取失敗；不再使用 reject-driven 盲抽模式。

背包查詢只新增讀操作；不改 `ws_token.gacha` 的協議編碼、bundle 成本或抽卡回包解析。

## Timeout 與斷線處理

- `ConnectionClosed`、`ConnectionReset`、`BrokenPipe`、client 已不再 running：視為確定
  transport loss，沿用既有「重連一次」處理。
- `WSTimeoutError` 且 client 仍 running：標記為「伺服器無回應」，不宣稱斷線，接著
  讀取 `0x0401` 與 `0x0901`。
- 券數減少正確成本且 pool count 增加正確抽數：請求已落地、只有 draw reply 遺失；
  計入該批並繼續。
- 券數與 pool count 都沒變：請求未落地；等待 1 秒安全間隔後最多重送一次。
- 兩個探測互相矛盾、任一探測持續讀不到，或重送仍 timeout：停止並標示
  `unconfirmed`，不猜測、不再重送。
- fixed 與 drain 共用相同確認規則；只有雙探測確定未落地時才允許重送，避免超出指定批數。

## UI 與工作結果

- 確定斷線才顯示「WS 斷線」。
- timeout 顯示「伺服器無回應」，不使用「傳輸錯誤」誤導使用者。
- 正常耗盡仍以 `status=done`、`stopped_reason=exhausted` 完成。
- 探測確認已落地的 timeout 批次加入總抽數，log 標示「狀態探測確認成功」。
- 無法確認的 timeout 保留已確認抽數，`stopped_reason` 記錄 `unconfirmed`；不把該批
  加入總抽數。

## 測試

- 背包有 800 張券：只送一次 999，接著正常 exhausted，不會送第二個 999。
- 背包有 845 張券：依序送 999、35、15，最後正常 exhausted。
- 連續 request 的 send-start 間隔不小於 1 秒，sleep 只補足剩餘差額。
- 起始 `0x0401`／`0x0901` 查詢失敗：不開始付費抽卡。
- draw timeout 後券數與 pool count 都前進：計入成功，不重送。
- draw timeout 後兩者都不變：間隔滿 1 秒後只重送一次。
- draw timeout 後雙探測矛盾或不可讀：停止為 `unconfirmed`。
- 明確連線關閉：仍重連一次，既有行為不退化。
- fixed 模式只在雙探測確定未落地時重送，不多算批次。

驗證只執行抽卡與 WS client 相關目標測試，以及修改檔案的 `py_compile`；不跑整包
pytest，避免載入真裝置與影像依賴。
