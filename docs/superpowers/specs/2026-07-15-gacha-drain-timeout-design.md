# 純 WS 一鍵抽完 timeout 修復設計

## 問題與根因

Dashboard 的純 WS 抽卡會送 `0x0902`，並等待 `0x0902` 成功回包或
`0x0201`（十進位 `513`）拒絕回包。`WSTimeoutError` 只代表指定時間內兩種
回包都沒到，不等於 WebSocket 已斷線。

目前 dashboard 沒有讀取技能券 `1012`／同伴券 `1013` 的實際餘額，
`remaining` 永遠是 `None`。因此第一批 999 抽成功、消耗 800 張券後，程式仍會
盲送下一批 999。伺服器若對不可負擔的請求保持靜默，10 秒後便被記成「傳輸錯誤」；
既有測試又明定一般 timeout 不重連、直接中止，於是畫面同時顯示已完成 999 抽與
timeout。

## 目標

- 一鍵抽完以權威背包餘額選擇 999／35／15，不靠錯誤回包探測券數。
- 區分「伺服器無回應」與「確定斷線」，不再把所有 timeout 稱為斷線或傳輸錯誤。
- drain 模式即使餘額查詢失敗，也能在無回應時安全降階，不因一個靜默請求整體報錯。
- fixed 模式維持保守：回包不明時停止，避免重送造成超出指定批數。

## 資料流

1. 工作取得持久 `WSGameClient` 後，以既有 `0x0401` 全背包查詢讀取對應抽券數量。
2. 若讀取成功，使用既有固定成本 `999→800`、`35→30`、`15→15` 選擇最大可負擔檔位。
3. 每批收到 `0x0902` 成功回包後，從本地權威起始餘額扣除該檔成本，再選下一檔。
4. 餘額低於 15 時以 `exhausted` 正常完成，不再送必定不可負擔的封包。
5. 若 `0x0401` 查詢失敗，保留 reject-driven 階梯作為降級路徑。

背包查詢只新增讀操作；不改 `ws_token.gacha` 的協議編碼、bundle 成本或抽卡回包解析。

## Timeout 與斷線處理

- `ConnectionClosed`、`ConnectionReset`、`BrokenPipe`、client 已不再 running：視為確定
  transport loss，沿用既有「重連一次」處理。
- `WSTimeoutError` 且 client 仍 running：標記為「伺服器無回應」，不宣稱斷線。
- drain + 未知餘額：該檔無回應時降到下一檔繼續；不重送同一檔，避免回包遺失時
  重複扣券。
- fixed：無回應即停止，保留已確認批數並顯示原因。
- 已知餘額下若可負擔請求仍 timeout：停止並顯示「伺服器無回應」，因為這不再是正常的
  券不足邊界，不能假裝抽卡成功。

## UI 與工作結果

- 確定斷線才顯示「WS 斷線」。
- timeout 顯示「伺服器無回應」，不使用「傳輸錯誤」誤導使用者。
- 正常耗盡仍以 `status=done`、`stopped_reason=exhausted` 完成。
- 未確認的 timeout 保留 `status=done` 與已確認抽數，但 `stopped_reason` 明確記錄
  `no_response`；不把未收到回包的批次加入總抽數。

## 測試

- 背包有 800 張券：只送一次 999，接著正常 exhausted，不會送第二個 999。
- 背包有 845 張券：依序送 999、35、15，最後正常 exhausted。
- `0x0401` 查詢失敗：沿用盲階梯；999 timeout 後降到 35，而非整個工作報錯。
- 已知餘額且可負擔的 draw timeout：停止並標示 `no_response`，不誤稱斷線。
- 明確連線關閉：仍重連一次，既有行為不退化。
- fixed 模式 timeout：不重送、不多算批次。

驗證只執行抽卡與 WS client 相關目標測試，以及修改檔案的 `py_compile`；不跑整包
pytest，避免載入真裝置與影像依賴。
